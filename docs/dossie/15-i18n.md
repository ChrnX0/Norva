## 15. Idiomas, moeda e região

O sistema de idiomas deste aplicativo não é uma biblioteca com um arquivo de tradução ao
lado: é um tipo TypeScript que **quebra a compilação** quando uma das três traduções
falta, um dicionário de 897 frases escrito por seção de tela, um punhado de formatadores
que embrulham `Intl`, e sete redes de teste que cobrem sete frestas diferentes que a
compilação não vê. Não há dependência de terceiros para nada disso — a decisão está
escrita: *"Deliberately tiny: this app has no need for a full i18n runtime, and a
dependency here would be weight for nothing"* (`src/i18n/index.ts:37-38`).

### 15.2 `Widen<T>`: como a compilação obriga as três traduções

O português é a língua fonte, e o objeto é congelado com `as const`
(`src/i18n/locales/pt-BR.ts:13` abre `export const ptBR = {`, e `:1168` fecha com
`} as const;`).

Sem mais nada, `as const` daria a cada folha o tipo do **texto literal** — `'Confirmar'`,
não `string` — e nenhuma tradução poderia satisfazer esse tipo. A solução é uma linha:

```ts
type Widen<T> = T extends string ? string : { [K in keyof T]: Widen<T[K]> };

export type Dictionary = Widen<typeof ptBR>;
```

(`src/i18n/locales/pt-BR.ts:1176` e `:1178`; o docblock em `:1170-1175` diz a razão:
*"Widens every leaf string to `string` while keeping the shape intact. […] Structure is
checked, wording is free."*)

`Widen<T>` é **recursivo e estrutural**: para cada folha `string` devolve `string`; para
cada objeto, devolve um objeto com as MESMAS chaves, aplicando `Widen` a cada valor. O
resultado é um tipo que exige a árvore inteira e não exige palavra nenhuma.

As duas traduções então se declaram assim:

| Arquivo | Declaração |
|---|---|
| `src/i18n/locales/en.ts:4` | `export const en: Dictionary = {` |
| `src/i18n/locales/es.ts:9` | `export const es: Dictionary = {` |

`Widen<T>` **não é exportado** — quem sai do arquivo é `Dictionary`, reexportado em
`src/i18n/index.ts:6` (`export type { Dictionary };`).

#### O que `Widen<T>` garante, e o que ele não garante

| Garante | Não garante |
|---|---|
| Chave nova em pt-BR quebra `tsc` em `en.ts` e `es.ts` até ser escrita | Que a frase traduzida diga a mesma coisa |
| Chave sobrando numa tradução também quebra (excesso de propriedade) | Que a frase traduzida conserve os `{{buracos}}` do original |
| Aninhamento igual nos três (um objeto não vira string) | Que alguma tela leia a chave |
| Um par plural `{one, other}` existe nos três | Que a tela USE a chave em vez de escrever a frase na mão |

As três lacunas da coluna da direita são exatamente o que os testes de §15.17 fecham. A
frase está escrita duas vezes no repositório, com as mesmas palavras: *"O `Widen` não pega
isto: ele obriga a chave a existir nos três dicionários, nunca a tela a usá-la"*
(`src/i18n/locales/pt-BR.ts:1065-1066`, e de novo em `src/layers.test.ts:138-139`).

### 15.3 `LanguageTag`, `LocaleSettings` e `defaultLocale`

```ts
export type LanguageTag = 'pt-BR' | 'es' | 'en';

const dictionaries: Record<LanguageTag, Dictionary> = { 'pt-BR': ptBR, es, en };
```

(`src/i18n/index.ts:8` e `:10`.) Note que o inglês e o espanhol são tags **sem região** —
a região entra depois, pela moeda (§15.6).

```ts
export type LocaleSettings = {
  language: LanguageTag;
  /** BCP 47 tag used for number and date formatting. */
  formatting: string;
  /** ISO 4217. */
  currency: string;
  timeZone: string;
};
```

(`src/i18n/index.ts:16-23`. O docblock em `:12-15`: *"Currency is a property of the
company, not of the phone. A Brazilian factory whose owner reads the app in English still
bills in BRL."*)

São quatro perguntas separadas de propósito, e a lição está escrita em
`docs/insights.md:3382-3385`: **"o tipo é uma lista de perguntas, e consertar um campo dele
obriga a olhar os vizinhos"** — a auditoria achou um campo chumbado (idioma) e dois
estavam errados (moeda e fuso).

O padrão do produto:

```ts
export const defaultLocale: LocaleSettings = {
  language: 'pt-BR',
  formatting: 'pt-BR',
  currency: 'BRL',
  timeZone: 'America/Sao_Paulo',
};
```

(`src/i18n/index.ts:25-30`.) `src/i18n/i18n.test.ts:85` afirma
`defaultLocale.language === 'pt-BR'`.

A resolução do dicionário é uma linha:

```ts
export function dictionary(language: LanguageTag): Dictionary {
  return dictionaries[language];
}
```

(`src/i18n/index.ts:32-34`.) Os três dicionários são importados **estaticamente** no topo
(`src/i18n/index.ts:1-3`): não há carregamento sob demanda, não há divisão de pacote por
idioma, e trocar de idioma não faz requisição nenhuma. **Estado: implementado e chamado** —
os únicos dois chamadores de `dictionary()` são `src/i18n/Locale.tsx:91` e `:109`.

### 15.4 Como se escolhe o idioma: as duas camadas, e qual ganha

A regra de produto está escrita por extenso no docblock do provedor
(`src/i18n/Locale.tsx:10-35`), e ela tem três afirmações:

1. **É fato da EMPRESA, não do aparelho.** *"a fábrica brasileira cujo dono lê inglês roda
   em português para todo mundo no chão de fábrica"* (`src/i18n/Locale.tsx:20-22`). Idioma
   e moeda ficam juntos numa escolha só de empresa; claro/escuro e as duas identidades
   visuais são preferência de quem segura o celular.
2. **O aparelho é o primeiro palpite, e só.** *"No dia em que a empresa nasce, o idioma vem
   do celular, a moeda vem do país do celular e o fuso vem do relógio dele […]. Depois
   disso, quem manda é o que ficou guardado"* (`src/i18n/Locale.tsx:26-30`).
3. **O fuso não é pergunta em nenhum momento**: o celular está no galpão
   (`src/i18n/Locale.tsx:32-34`).

#### A ordem de precedência, exata

Na montagem do provedor (`src/i18n/Locale.tsx:53-76`):

```ts
void Promise.all([readMeta(LANGUAGE_KEY), readMeta(CURRENCY_KEY)])
  .then(([language, currency]) => {
    const doAparelho: LocaleSettings = {
      language: detectLanguage(),
      currency: detectCurrency(),
      timeZone: detectTimeZone(),
      formatting: defaultLocale.formatting,
    };
    setLocale(localeFrom({ language, currency, timeZone: doAparelho.timeZone }, doAparelho));
  })
  .catch(() => undefined)
  .finally(() => { if (!cancelled) setReady(true); });
```

Ou seja, por campo:

| Campo | 1º | 2º | 3º |
|---|---|---|---|
| `language` | gaveta `locale.language`, se for uma das três tags | `detectLanguage()` do aparelho | `'pt-BR'` (dentro de `detectLanguage`) |
| `currency` | gaveta `locale.currency`, se estiver em `CURRENCIES` | `detectCurrency()` do aparelho | `'BRL'` (dentro de `detectCurrency`) |
| `timeZone` | **sempre** `detectTimeZone()` — nunca lido da gaveta | — | `'America/Sao_Paulo'` (dentro de `detectTimeZone`) |
| `formatting` | **sempre calculado**: `formattingFor(language, currency)` | — | — |

Duas consequências que se perdem se não forem ditas: o **fuso nunca é persistido** (não há
`locale.timeZone` no `app_meta`); e o campo `formatting` de `padrao` **nunca é lido**,
porque `localeFrom` sempre o recalcula (`src/i18n/company.ts:67`) — a linha
`formatting: defaultLocale.formatting` em `src/i18n/Locale.tsx:64` é inerte.

Enquanto a gaveta não responde, vale `defaultLocale` no `useState`
(`src/i18n/Locale.tsx:50`), com o comentário: *"O primeiro quadro do aplicativo não pode
esperar disco para escolher uma palavra"*. `ready` fica falso até o `finally`
(`:41-42`, `:70-72`). Se a leitura falha, o `catch` engole: *"Idioma é enfeite comparado a
abrir: sem resposta da gaveta, vale o padrão"* (`src/i18n/Locale.tsx:68-69`).

#### Onde a escolha da empresa mora

Duas chaves no `app_meta` local (`src/i18n/Locale.tsx:7-8`):

```ts
const LANGUAGE_KEY = 'locale.language';
const CURRENCY_KEY = 'locale.currency';
```

`app_meta` é uma tabela chave/valor do SQLite (`src/data/db.ts:136`), lida e escrita por
`readMeta`/`writeMeta` (`src/data/meta.ts:15-31`). O docblock dela avisa o que **não** cabe
ali: *"O que NÃO cabe é qualquer coisa que alguém vá somar. […] uma chave/valor é
exatamente o formato em que um `estoque_atual` renasceria"* (`src/data/meta.ts:10-13`).

Todas as chaves de preferência do aplicativo, com a camada de cada uma:

| Chave | Camada | Onde |
|---|---|---|
| `locale.language` | **empresa** | `src/i18n/Locale.tsx:7` |
| `locale.currency` | **empresa** | `src/i18n/Locale.tsx:8` |
| `appearance.skin` | aparelho | `src/theme/Appearance.tsx:8` |
| `appearance.hue` | aparelho | `src/theme/Appearance.tsx:9` |
| `appearance.scheme` | aparelho | `src/theme/Appearance.tsx:10` |
| `briefing.order` | **empresa** ("a ordem é da casa") | `src/data/repository.ts:3888` |

A tela de Ajustes diz a diferença em palavras, e a frase é decisão de produto
(`src/i18n/locales/pt-BR.ts:414-417`):

> **Idioma e moeda** — *"Escolha da empresa: vale para todo mundo que usa este sistema, não

contra, no cartão vizinho (`src/i18n/locales/pt-BR.ts:421`):

#### Escrita otimista

Os dois setters mudam a tela primeiro e gravam depois
(`src/i18n/Locale.tsx:78-88`):

```ts
const setLanguage = useCallback((language: LanguageTag) => {
```

### 15.5 O aparelho como palpite: `src/i18n/device.ts`

Este arquivo é separado de propósito: *"formatting money and picking words is arithmetic
that runs anywhere, while reading the device's locale is a native call. Separating them is
what lets the domain, the assistant and their tests use the formatters without dragging a
native module in"* (`src/i18n/device.ts:8-11`).

**`detectLanguage(): LanguageTag`** (`src/i18n/device.ts:13-18`) — prefixo, em ordem fixa:

```ts
const tags = getLocales().map((l) => l.languageTag.toLowerCase());
if (tags.some((t) => t.startsWith('pt'))) return 'pt-BR';
if (tags.some((t) => t.startsWith('es'))) return 'es';
return 'en';
```

Qualquer `pt-*` cai em `pt-BR` (não há pt-PT). Qualquer `es-*` cai em `es` sem região.
Tudo o mais é inglês.

**`detectCurrency(): string`** (`src/i18n/device.ts:30-36`) — primeira moeda do aparelho que
esteja na lista oferecida; senão `'BRL'`, *"que é o padrão do produto e a moeda da fábrica
onde ele nasceu"* (`:27-28`).

**`detectTimeZone(): string`** (`src/i18n/device.ts:46-49`):

```ts
const zone = getCalendars()[0]?.timeZone ?? '';
return zone.includes('/') ? zone : 'America/Sao_Paulo';
```

O teste da barra `/` é a régua de "é um nome IANA": `"GMT-3"` não serve para `Intl`. O
docblock diz por que isso não é enfeite: *"Isto decide qual DIA um tacho fechado às 22h
pertence, e o padrão chumbado em `America/Sao_Paulo` fazia uma fábrica em Manaus lançar
produção no dia errado — uma hora de diferença, todos os dias, no número que vai na
etiqueta"* (`src/i18n/device.ts:41-44`). O relato completo está em
`docs/insights.md:3369-3378`.

### 15.6 A moeda define a região

Esta é a decisão mais contraintuitiva do módulo, e ela tem docblock próprio
(`src/i18n/company.ts:3-18`):

> **Por que a moeda decide o formato, e não o idioma.** Espanhol escreve `1.234,56` na
> Espanha e `1,234.56` no México — o mesmo idioma, o ponto e a vírgula trocados de lugar.
> Um número de dinheiro lido ao contrário é a pior classe de erro que este aplicativo pode
> cometer, então quem manda no formato é a REGIÃO, e a região vem da moeda: quem cobra em
> peso mexicano está no México.

E a ressalva, na mesma nota: *"O idioma continua sendo escolha separada — alguém no México
pode querer o aplicativo em inglês e continuar cobrando em MXN."*

#### A lista fechada de moedas

```ts
export const CURRENCIES = [
  { code: 'BRL', region: 'BR' },
  { code: 'USD', region: 'US' },
  { code: 'EUR', region: 'ES' },
  { code: 'MXN', region: 'MX' },
  { code: 'ARS', region: 'AR' },
  { code: 'CLP', region: 'CL' },
  { code: 'COP', region: 'CO' },
  { code: 'PYG', region: 'PY' },
] as const;

export type CurrencyCode = (typeof CURRENCIES)[number]['code'];

export function isCurrency(code: string): code is CurrencyCode {
  return CURRENCIES.some((c) => c.code === code);
}
```

(`src/i18n/company.ts:19-34`.) Oito moedas, oito regiões. `EUR` é mapeado para `ES`
(Espanha) e não para a zona do euro — é uma escolha, não um padrão ISO.

Sobre moeda sem centavo: *"Guaraní e peso chileno não têm centavo, e o `Intl` sabe disso: o
valor inteiro que o livro-razão guarda continua sendo centésimo de unidade em toda moeda, e
só a escrita muda. É a mesma regra de sempre — arredonda no fim, uma vez"*
(`src/i18n/company.ts:15-17`).

#### `formattingFor(language, currency)`

```ts
export function formattingFor(language: LanguageTag, currency: string): string {
  if (language === 'pt-BR') return 'pt-BR';
  const region = CURRENCIES.find((c) => c.code === currency)?.region;
  return region ? `${language}-${region}` : language;
}
```

(`src/i18n/company.ts:43-47`.) Três regras:

1. `pt-BR` já é tag completa e **passa direto**, qualquer que seja a moeda. O teste afirma
   isso explicitamente: `formattingFor('pt-BR', 'USD') === 'pt-BR'`, com o motivo escrito —
   *"a fábrica que cobra em dólar e lê em português continua escrevendo número como o Brasil
   escreve"* (`src/i18n/i18n.test.ts:116-117`).
2. Para `es` e `en`, a região vem da moeda: `` `${language}-${region}` ``.
3. Moeda fora da lista cai no idioma sozinho — *"pior formato, nunca erro"*
   (`src/i18n/company.ts:41`). O teste: `formattingFor('es', 'JPY') === 'es'`
   (`src/i18n/i18n.test.ts:123`).

A grade completa das 24 combinações, com a tag gerada e a tag que o ICU resolve
(medido rodando `Intl.NumberFormat(...).resolvedOptions().locale` no Node deste
repositório):

| moeda | região | pt-BR → | es → | en → |
|---|---|---|---|---|
| BRL | BR | `pt-BR` (→pt-BR) | `es-BR` (→es-BR) | `en-BR` (→en) |
| USD | US | `pt-BR` (→pt-BR) | `es-US` (→es-US) | `en-US` (→en-US) |
| EUR | ES | `pt-BR` (→pt-BR) | `es-ES` (→es-ES) | `en-ES` (→en-ES) |
| MXN | MX | `pt-BR` (→pt-BR) | `es-MX` (→es-MX) | `en-MX` (→en) |
| ARS | AR | `pt-BR` (→pt-BR) | `es-AR` (→es-AR) | `en-AR` (→en) |
| CLP | CL | `pt-BR` (→pt-BR) | `es-CL` (→es-CL) | `en-CL` (→en) |
| COP | CO | `pt-BR` (→pt-BR) | `es-CO` (→es-CO) | `en-CO` (→en) |
| PYG | PY | `pt-BR` (→pt-BR) | `es-PY` (→es-PY) | `en-PY` (→en) |

Observação factual, não corrigida no código: a combinação **espanhol + real** gera
`es-BR`, uma tag sintética que o CLDR resolve com a convenção latino-americana
(`12,345.67`) e não com a brasileira (`12.345,67`). O caso é exercitado por
`src/i18n/i18n.test.ts:163`, que afirma `outro.formatting === 'es-BR'` quando a moeda
pedida é inválida e cai no padrão `BRL`.

#### O separador decimal, provado

`src/i18n/i18n.test.ts:113-146` é o caso que sustenta a decisão. Ele formata **a mesma
quantia** duas vezes:


### 15.7 Interpolação: `fill`

```ts
export function fill(template: string, values: Record<string, string | number> = {}): string {
  return template.replace(/\{\{(\w+)\}\}/g, (match, key: string) =>
    key in values ? String(values[key]) : match,
  );
}
```

(`src/i18n/index.ts:40-44`.) O marcador é `{{nome}}`, com `\w+` — letras, dígitos e

### 15.8 Plural

```ts
export function plural(
  n: number,
  variants: { one: string; other: string },
  display?: string,
): string {
  const text = fill(n === 1 ? variants.one : variants.other, { n: display ?? n });
  const nowhereToPutIt = !variants.one.includes('{{n}}') && !variants.other.includes('{{n}}');
  if (display !== undefined && nowhereToPutIt) return `${display} ${text}`;
  return text;
}
```

(`src/i18n/index.ts:55-89`.) Quatro decisões de projeto embutidas:

1. **Duas formas apenas, `one` e `other`, e a regra é `n === 1`.** Não há
   `Intl.PluralRules`, não há `few`/`many`/`zero` — verificado: `PluralRules` não aparece
   em lugar nenhum de `app/` ou `src/`. Zero cai em `other`.
2. **Singular e plural são frases inteiras, não um número colado num substantivo.** *"O
   verbo tem que concordar, e ele não concorda com um placeholder: o português precisa de
   'apaga 1 insumo' contra 'apaga 6 insumos', e uma língua que flexiona mais que isso
   escreve as duas metades ela mesma"* (`src/i18n/index.ts:47-53`, parafraseado do original
   em inglês).
3. **O terceiro parâmetro `display` separa o número que ESCOLHE do número que SE LÊ.** *"Um
   milhar de unidades é '1.000' em português e '1,000' em inglês, e a contagem que escolhe o
   ramo não é a string que vai na frase"* (`src/i18n/index.ts:58-62`).
4. **A regra `nowhereToPutIt` olha a ENTRADA inteira, não a forma escolhida.** Esse é o
   ponto que custou duas cicatrizes, e o docblock as narra (`src/i18n/index.ts:67-85`):

   - `units.unit` é `{one: 'unidade', other: 'unidades'}` — **sem** `{{n}}`, porque metade
     das telas a usa ao lado de um número que elas mesmas escrevem. Chamada com um número
     para mostrar, ela devolvia a palavra sozinha, e o cartão da capa anunciou uma falta sem
     dizer de quanto: *"Picolé de morango · unidades"*. *"Compilou, passou na suíte, e só o
     navegador viu."*
   - `batchCount` é o contrário: `{one: 'uma vez', other: '{{n}} vezes'}` — o singular
     escreve o número por extenso **de propósito**, e prefixar ali produziu *"em 1 um
     tacho"* na confirmação de produção; *"o e2e pegou na mesma rodada"*.

   Daí a régua final: quando **nenhuma** das duas variantes tem onde receber o número, ele
   vai na frente; quando **alguma** tem, a língua já decidiu.

O caso `src/i18n/i18n.test.ts:59-79` fixa as cinco situações:

| chamada | resultado |

| `plural(300, {one:'unidade', other:'unidades'}, '300')` | `300 unidades` |
| `plural(1, {one:'unidade', other:'unidades'}, '1')` | `1 unidade` |
| `plural(1, {one:'um tacho', other:'{{n}} tachos'}, '1')` | `um tacho` |
| `plural(2, {one:'unidade', other:'unidades'})` | `unidades` |

A mutação `src/i18n/index.ts` → `const nowhereToPutIt = false;` está registrada em
`scripts/mutate.mjs:505-510`, com o dano nomeado: *"o numero some da frase que nao tem onde
recebe-lo, e o cartao anuncia uma falta sem dizer de quanto"*.

#### Instante contra data de calendário — a distinção que gerou três funções

`formatDate`, `formatTime`, `formatWeekday` e `formatDayMonth` recebem um **instante ISO** e
o traduzem para o fuso da fábrica. `formatCalendarDate` e `formatWeekdayInitial` recebem
uma **data `YYYY-MM-DD`** e usam `timeZone: 'UTC'` fixo. O docblock explica
(`src/i18n/index.ts:180-187`):

> Uma data de calendário (`YYYY-MM-DD`) dita sem passar por fuso nenhum. […] Uma data
> combinada não tem hora: passada pelo mesmo caminho, "2026-09-03" vira meia-noite em UTC e
> aparece como 02/09 para quem está em São Paulo. O dia do compromisso é o que foi escrito.

`formatWeekdayInitial` usa `narrow` e não `short` porque a coluna tem um sétimo da tela: em
português "seg." não cabe (`src/i18n/index.ts:203-206`).

`formatWeekdayShort(weekday: number, …)` recebe o índice de `Date.getDay()` e o converte em
palavra usando um domingo de referência — `Date.UTC(2026, 8, 6)` — somando
`weekday * 86_400_000` (`src/i18n/index.ts:239-245`). O teste
`src/i18n/i18n.test.ts:88-102` confere as sete posições contra o `Intl` direto, e afirma
antes que a data de referência é mesmo domingo (`domingo.getUTCDay() === 0`). A razão
escrita: *"Se esta tabela andar um dia, a loja de terça passa a receber na quarta e nada
mais no app acusa"*.

#### `formatPacked`: a quantidade dita na embalagem que a pessoa carrega

```ts
export function formatPacked(
  baseUnits: number,
  hierarchy: PackagingHierarchy,
  words: Record<string, { one: string; other: string } | undefined>,
  locale: LocaleSettings,
  and?: string,
): string {
  const parts = breakdown(baseUnits, hierarchy).map((part) => {
    const entry = words[part.tier.id];
    const word = entry ? (part.quantity === 1 ? entry.one : entry.other) : part.tier.id;
    return `${formatQuantity(part.quantity, locale)} ${word}`;
  });
  return and ? joinList(parts, and) : parts.join(' · ');
}
```

`words` é **sempre `t.units`** nos três chamadores, indexado pelo `tier.id` da hierarquia —
uma leitura dinâmica do dicionário. Sem entrada, cai no próprio `tier.id` cru. O separador
padrão é `' · '`; passando `and` (sempre `t.common.and`), usa `joinList`. Regra escrita:
*"As camadas maiores vêm primeiro e o resto fica em unidades: 263 é '5 caixas · 13
unidades', nunca só '5 caixas', porque treze picolés que existem teriam desaparecido da
frase"* (`src/i18n/index.ts:141-145`, parafraseado).

Chamadores: `app/production/new.tsx:367` (sem `and`), `app/products/index.tsx:98` (com
`t.common.and`), `app/(tabs)/transport.tsx:98` (sem `and`).

A armadilha registrada: item **sem** camada de caixa (açúcar, polpa, palito) tem só a faixa
`unit`, e mandá-lo por aqui faz o aplicativo chamar grama de "unidade" — *"a capa dizia
'6.000 unidades de Açúcar cristal' para seis quilos"*
(`src/data/repository.ts:3271-3278`). Os dois chamadores que podem receber item solto
desviam para `` `${formatQuantity(...)} ${item.baseUnit}` ``
(`app/(tabs)/index.tsx:217` e `app/(tabs)/transport.tsx:96-99`).

#### `joinList`

```ts
export function joinList(parts: readonly string[], and: string): string {
  if (parts.length === 0) return '';
  if (parts.length === 1) return parts[0];
  return `${parts.slice(0, -1).join(', ')} ${and} ${parts[parts.length - 1]}`;
}
```

(`src/i18n/index.ts:261-265`.) A conjunção vem do dicionário: `common.and` é `e` / `and` /

último item é o que faz uma confirmação soar como frase que alguém escreveu"*
(`src/i18n/index.ts:256-259`, parafraseado).

**Ordenação sensível ao idioma NÃO ESTÁ NO CÓDIGO**: `localeCompare`, `Intl.Collator`,

(`app/recipes/index.tsx:141`, `app/losses.tsx:98`, `app/(tabs)/index.tsx:105`, `:309`).

#### O fuso, do outro lado: `src/domain/day.ts`

`locale.timeZone` é lido em **53 lugares** de telas, quase sempre passado para
`localDate(nowIso(), locale.timeZone)` ou `dayWindow(nowIso(), locale.timeZone, dias)`.

Essas duas funções também usam `Intl`, mas com tag **fixa e de máquina**, não do usuário:
`'en-CA'` em `src/domain/day.ts:38` e `:55` (porque `en-CA` formata `YYYY-MM-DD`, que é
justamente o formato que o código quer de volta) e `'en-US'` em `:95` para medir o
deslocamento do fuso. `localMidnight` mede o deslocamento **em cada extremidade** porque no
dia em que o relógio muda o dia tem 23 ou 25 horas (`src/domain/day.ts:70-90`).

Isto é o que faz o fuso não ser enfeite: `localDate(...)` decide o `producedOn` do lote
(`app/production/new.tsx:321`, `:332`), que vai **impresso na etiqueta**.

### 15.10 Números digitados: `parseTyped` e `formatTyped`

Fora do módulo `i18n`, mas parte do mesmo assunto: `src/domain/number.ts` é o único leitor e
o único escritor de número em campo de texto, e os dois são inversos
(`src/domain/number.ts:19`).

`parseTyped(raw: string): number | null` (`:32-75`) — **o último separador é o decimal**; os
outros agrupam. Regras exatas:

- limpa tudo que não é dígito, ponto, vírgula ou menos;
- com vírgula E ponto presentes, o **último** é o decimal;
- só vírgulas: uma é decimal, mais de uma é agrupamento;
- só pontos: um é decimal, mais de um é agrupamento;
- **exceção do milhar**: um ponto único com exatamente três dígitos depois e parte inteira
  diferente de zero é agrupamento — `1.250` é mil duzentos e cinquenta, `0.500` mantém o
  decimal. A mesma regra **não** é aplicada à vírgula, de propósito: *"tratar '1,500' como
  mil e quinhentos quebraria a língua em que este aplicativo é escrito para resgatar a que
  ele não é"* (`src/domain/number.ts:56-59`).

O motivo de existir: o app tinha três leitores diferentes; quatro telas faziam
`s.replace(/\./g, '').replace(',', '.')` (`118.50` → `11850`) e quatro faziam
`s.replace(',', '.')` (`46.000` → `46`, `1.000,00` → `NaN`). E o React Native substitui o
listener de teclado do Android por um que *"permits all keyboard input through"*, então
ponto e vírgula chegam qualquer que seja o teclado (`src/domain/number.ts:5-13`).

`formatTyped(value, formatting, maxDecimals = 4)` (`:85-90`) — `Intl.NumberFormat` com
`useGrouping: false`, porque *"agrupamento é exatamente a ambiguidade que este módulo existe
para remover, e um campo não é um relatório"*. O separador decimal é o do idioma: um
brasileiro vê `2,5` e um americano vê `2.5`, e os dois voltam como 2.5
(`src/domain/number.ts:80-83`).

Note que `formatTyped` recebe a **tag de formatação** (string), não `LocaleSettings` — é o
único formatador do repositório com essa assinatura.

### 15.14 A notificação: `alertPhrase`

`src/notify/phrase.ts:20-51` é a única montagem de frase fora de uma tela, e ela é função
pura de propósito — *"regra que mora em componente é regra que o `mutate` não alcança e que
nenhum teste importa"* (`src/notify/phrase.ts:8-9`).

```ts
export function alertPhrase(alert: Alert, t: Dictionary): { title: string; body: string } {
  const words = t.alertText[alert.kind];
  const amount =
    alert.kind === 'insumo' || alert.kind === 'validade'
      ? plural(Math.max(0, Math.floor(alert.amount)), t.app.home.dayCount)
      : alert.kind === 'ambiente'
        ? String(Math.round(alert.amount * 10) / 10)
        : String(Math.round(alert.amount));
  const valores = {
    subject: alert.subject,
    amount,
    unit: alert.unit ?? '',
    places: alert.places === undefined ? '' : plural(alert.places, t.app.home.placeCount),
  };
  return { title: fill(words.title, valores), body: fill(words.body, valores) };
}
```

A unidade de cada aviso é decisão registrada do dono (`src/notify/phrase.ts:26-32`): dias
para insumo e validade, porcentagem para volume, lojas para pedido, grandeza física para
ambiente — *"Um número solto sem a unidade dele é a mesma coisa que nenhum número."* E o
caso `ambiente` guarda a fração (uma casa decimal) porque *"meio grau de freezer é diferença
real"*.

Chamador único: `src/notify/Alerts.tsx:31`, dentro de
`rescheduleAlerts(locale.timeZone, (alert) => alertPhrase(alert, t))`.

**Observação factual sobre o idioma da notificação**: `t` vem do provedor, então a
notificação é agendada no idioma vigente **no momento do agendamento**. Trocar o idioma
depois não reescreve avisos já agendados — só o próximo `rescheduleAlerts` faz isso.

#### 15.17.4 `src/layers.test.ts` — o guard de frase crua e o de porcentagem à mão

Este é o arquivo que pega texto em português escrito dentro de uma tela.

**`no screen writes a sentence of its own`** (`src/layers.test.ts:184-208`). A cicatriz está
no docblock (`:131-152`): o `WhySheet` — *"a folha que abre a conta de toda conclusão do
aplicativo, a Lei 6 em pessoa"* — tinha "Custo do lote", "Perda prevista" e "Fechar"

A régua não é acento — e essa correção tem história: *"a primeira versão deste caso
procurava acento e se dizia capaz de ter pegado o `WhySheet`. 'Custo do lote' não tem acento
nenhum. O guard passaria verde na própria cicatriz que ele cita, o que é pior que não
existir: ele anunciaria uma proteção que não estava lá"* (`:141-145`).

A régua é **palavra funcional + espaço + não ser caminho** (`pareceFrase`, `:166-174`):

```ts
const PALAVRAS = ['do', 'da', 'de', 'no', 'na', 'em', 'para', 'por', 'com', 'que'];

function pareceFrase(linha: string): boolean {
  const literais = linha.match(/(['"`])[^'"`]{4,}\1/g) ?? [];
  return literais.some((bruto) => {
    const texto = bruto.slice(1, -1).replace(/\$\{[^}]*\}/g, ' ');
    if (!texto.includes(' ')) return false;
    if (texto.includes('/') || texto.includes('=')) return false;
    return new RegExp(`\\b(${PALAVRAS.join('|')})\\b`, 'i').test(texto);
  });
}
```

Cada uma das três condições saiu de um alarme falso que custou uma rodada (`:157-161`):
`'as'` na lista acusava `as Draft['kind']` porque `as` é palavra-chave do TypeScript; sem
exigir espaço, `'input'` casava; sem excluir caminho, `'@/domain/day'` casava com "do". A
interpolação sai antes da conta porque `${formatQuantity(...)}` é composição de pedaço já
traduzido.

Escopo: `app/` + `src/components` + `src/home` + `src/notify` (`screenLayers`, `:177-182`).
`src/data` fica fora porque *"semeia exemplo, e exemplo é dado"* (`:176`). Linhas de
`import`, `from '@…'`, `router.push`/`replace`, `getByLabel` e `goto(` são puladas
(`:195`). Comentário é para humano — `code()` remove `/* */` e `//` (`:24-26`).

O caso-espelho `the sentence guard bites the real scar` (`:210-228`) prova as duas direções:
`pareceFrase("<Text>{'Custo do lote'}</Text>")` reprova, e os quatro inocentes passam.

**`no screen builds a percentage by hand`** (`:502-519`), com `porCentoNaMao` (`:489-500`):
linha a linha, casa `/\*\s*100\s*\)?\s*\.toFixed\(/` **e** contém `%`. As duas condições são
necessárias: sem o `%`, a régua acusa o próprio docblock de `formatPercent`, que cita o
padrão em prosa, e a tela da receita, que arredonda para duas casas e entrega a
`formatTyped` — *"que sabe o idioma"* (`:492-495`). O caso-espelho (`:521-542`) prova que

### 15.18 Fronteiras registradas e o que não existe

**O assistente fala um idioma só, e é decisão escrita.** `src/assistant/index.ts:7-22`:

> The assistant speaks Portuguese only, and that is a boundary rather than an oversight.
> The screens read every word from the dictionary and run in three languages. The assistant
> cannot follow yet, because what it matches on is Portuguese phrasing: "quanto custa",
> "comprei 4 sacos de". Translating the answers would be half a job - the questions would
> still only arrive in one language, and an assistant that answers in Spanish but only
> understands Portuguese is worse than one that is honestly monolingual.

E como termina: quando um modelo de linguagem fizer o casamento, *"as respostas vão para o
dicionário então, na mesma mudança"*. Consequências no código: `app/assistant.tsx:100` passa
`locale: defaultLocale` ao contexto do assistente (e não o locale da empresa) — mas
`app/assistant.tsx:98` passa `locale.timeZone` de verdade para `liveData`. E
`src/assistant/text.ts:84` tem `movePhrase(change, locale = defaultLocale)` com um docblock
que separa as duas coisas: *"O assistente fala português por decisão escrita […] e a decisão
é sobre as PALAVRAS dele; número formatado à mão é a família de defeito que este projeto já
pagou caro, e não precisa de exceção nenhuma aqui"* (`src/assistant/text.ts:79-83`) — por
isso ele usa `formatPercent`.

O que **NÃO ESTÁ NO CÓDIGO**, verificado por varredura:

| ausente | verificação |
|---|---|
